二、全局铁律（每条都必须遵守，违反即返工）
─────────────────────────────────────────────
1. 全程中文：进度输出、commit message、代码注释、交付文档一律中文。
2. 自主闭环工作流：每个任务「方案 → 实现 → 自测 → 自我 Review →
   迭代直至全部验收标准达成 → 记录 → 下一任务」。一个任务没闭环，
   不进入下一个；多个任务不许糊在一起交付。
3. 不破坏既有功能：每个任务完成后必须 npm run build 通过，并回归核心
   路径（书库浏览 / 阅读器 / 智学聊天 / 登录态）。凡是动了阅读器相关
   代码，必须回归「高亮/笔记完整标记选中文本」这个历史高发 bug。
4. 数据安全：改 Supabase 表结构用项目既有的数据库变更方式执行；所有
   新表必须配 RLS 并实测验证；涉及老数据的变更先备份再迁移（迁移
   SQL 与备份方式记入决策记录），严禁丢数据。
5. 秘钥安全：MiniMax key 等一律只在服务端使用，严禁下发到客户端；
   交付文档中不得出现任何明文秘钥。
6. 部署相关已知坑：vercel.app 域名国内被墙，线上验证一律走
   goodcontent.cn；写 env 须用 bash printf；dev 与 next start 共用
   .next 会互相污染。
7. commit 风格沿用现有仓库习惯（中文 + feat/fix 等前缀），按任务
   分批提交，每个任务至少一个独立 commit，便于回溯。
8. 自测诚实原则：能自动化验证的（构建、接口 curl、无头浏览器 E2E、
   数据库查询核对）必须实际执行并留存证据；确实无法自动化的（真机
   触感、移动端麦克风权限弹窗等），在《验收清单》中如实标注
   「待人工真机复核」并写清复核步骤，严禁谎报已验证。
9. 中断韧性（IMPORTANT）：执行途中你（Claude Code）可能被强制
   暂停——最典型的是用户的 Claude 订阅会员 Token 达到该时段上限，
   你会被停下，等额度恢复后会话才能继续；也可能是会话被关闭后
   新开会话接续、上下文被压缩等。所有这类情况一律视为「暂停
   等待」，绝不视为「任务结束」。处理方式：
   ① 平时就把当前进度、断点位置、剩余待办持续落盘到
      docs/delivery/progress.md（每完成一个任务就更新，保证任何
      时刻被掐断都有据可续，不依赖记忆和会话上下文）；
   ② 额度恢复、会话继续（含开了新会话来接续）后，第一件事是重读
      progress.md 与本任务书，并用 git log 核对代码实际进度，确认
      断点后无损续跑——不重做已完成的，不漏做未完成的；
   ③ 严禁因为被暂停过而降低标准：不许跳过未完成的验收步骤、不许
      缩水交付物、不许把"中途被停过"当作某项任务做不完的理由——
      暂停只影响进度时间，不改变「高质量完成任务书全部内容」这一
      最终目标。

【T5】全量切换 MiniMax 最新模型 M3 + 上下文压缩放宽
- 模型切换：lib/server/minimax.ts 默认模型由 MiniMax-Text-01 改为
  MiniMax 最新的 M3。执行时先查 MiniMax 官方文档/接口实测确认确切
  模型 ID（写最小脚本调用验证），不许猜；确认过程记入决策记录。
- 全局排查所有模型引用点：智学主对话、压缩摘要模型（COMPRESS_MODEL）、
  以及本任务书新增的 Memory 更新、语音、联网搜索等调用，全部统一
  为 M3。
- 注意：M2 输出带 <think> 思考段；切 M3 后必须实测其输出格式，若也
  有思考段，流式解析必须正确剥离，不得把思考内容漏给用户。
- Agentic 能力释放（IMPORTANT，不止换模型 ID）：M 系模型的招牌是
  工具循环中的连续思考（interleaved thinking），官方要求把模型的
  思考内容回灌到后续请求的 assistant 历史中，否则每轮工具调用都会
  "失忆"、显著降智。当前实现恰好相反——makeThinkFilter 把 <think>
  段直接丢弃（lib/server/minimax.ts），runAgent 回灌历史时只放已剥
  思考的文本（app/api/chat/route.ts）。切 M3 后必须改造：工具循环
  内部完整保留并回灌思考内容（具体字段形态以官方文档 + 实测为准）；
  面向用户不直接展示思考原文，而是按 T8 的「思考过程包装展示」规范
  转为友好的过程提示；同时评估 MAX_ROUNDS=5 的轮次上限是否需要
  上调，以匹配 M3 的多步规划能力（T10 联网搜索上线后尤其需要）。
- 压缩放宽：lib/server/compress.ts 当前摘要上限 maxTokens=1500，压得
  太猛。调整为：触发口径维持 500K（现以消息条数做代理），压缩产物
  放宽到约 5K tokens——即「500K 触发 → 压到 5K 即可」。
- 完成标准：① 全仓 grep 无 Text-01/M2 残留引用；② 实测一次真实
  压缩，产物长度约 5K 并留存样本；③ 流式输出实测无思考段泄漏、
  无格式异常；④ 思考链回灌生效：留存一次多轮工具调用的请求日志，
  核对第二轮请求的历史中包含第一轮的思考内容。

【T6】完善长按语音输入（走 MiniMax TokenPlan 接口）
- 现状：app/chat/page.tsx 已有语音雏形，需完善为完整可用的功能。
- 交互规范（参考微信水准）：长按说话 → 松开发送 → 上滑取消；录音中
  有音量波动动效与计时；权限被拒/录音失败有优雅兜底提示。
- 识别链路：录音上传 → 服务端代理调用 MiniMax TokenPlan 的语音识别
  接口（key 已在项目 env 中，严禁暴露给客户端）→ 识别文本回填输入框
  供用户确认后发送（默认方案；若实测体验更优可改为直接发送，决策
  记入决策记录）。
- 兼容性：调研并处理 iOS Safari 与微信内置浏览器的 getUserMedia /
  录音格式限制（如 webm/mp4/wav 的取舍与转码），实现降级方案。
- 完成标准：① 桌面浏览器无头/有头环境完成录音→识别→回填全链路
  自测并留存证据；② ASR 接口用真实音频样本实测识别成功；③ iOS/
  Android 真机触感项在《验收清单》中标注「待人工真机复核」并附
  详细复核步骤；④ 无 key 泄漏（检查客户端 bundle）。

【T7】每用户持久化 Memory 记忆系统（放开想象，让小涤「更懂他」）
- 目标：用户长期使用后，小涤对其有越来越清晰的认知，体感是「小涤
  记得我、懂我」。
- 数据库：在 Supabase 设计一张用户记忆表（如 user_memory），字段即
  记忆的不同维度，建议包含（可再发挥）：身份画像、阅读偏好（题材/
  深浅/节奏）、兴趣主题、聊天风格偏好、重要个人事实、近期关注、
  待跟进事项等；外加 updated_at 等元数据。每用户一行。RLS：仅本人
  可读，写入仅限服务端 service role。
- 更新机制（核心约束：全程服务端异步、客户端完全无感）：
  ① 实现一个服务端 Memory 工具/模块：输入 = 该用户记忆表现值 + 最新
     对话内容，由大模型（M3）判断哪些维度需要更新并产出新值，增量
     合并写回对应字段；
  ② 触发时机：聊天过程中由服务端自行触发（如每轮回复完成后或每 N 轮
     fire-and-forget 异步执行），绝不阻塞流式回复，客户端不出现任何
     loading 或延迟感知；注意 Vercel serverless 环境下 fire-and-forget
     的执行保障（如 waitUntil），方案记入决策记录；
  ③ 防膨胀：每个字段设长度上限，更新时由模型做取舍压缩，保留最有
     价值的认知。
- 注入机制：每次对话开始时，将该用户记忆摘要注入 system prompt，
  让小涤的回答自然体现对用户的了解（不要生硬复述记忆内容）。
- 完成标准：① 自测脚本模拟聊天透露个人信息（如「我喜欢看历史类
  的书」）→ 查表确认异步落表，留存前后数据对比；② 新一轮对话实测
  小涤的回答体现该认知，留存对话样本；③ 实测流式回复耗时与未开启
  Memory 时无可感知差异；④ RLS 实测：A 用户 token 查不到 B 用户记忆。

【T8】工具调用文案与等待占位 → 「文字水波纹」动效（去掉一切「...」）
- 范围：① 工具调用时展示的状态文案（lib/server/tools.ts 的 toolStatus
  产出文案中含「...」的全部清理）；② 大模型尚未开始流式输出前的等待
  占位文案；③ 模型思考过程的包装展示（见下）。
- 思考过程包装展示（与 T5 联动）：M3 的 <think> 思考内容不向用户
  展示原文，由服务端加工成面向用户的过程提示短句，让用户明白小涤
  此刻正在帮他做什么、缓解等待焦虑（例：「正在书架间为你翻找合适
  的书」「在比较哪一章最能回答你的问题」）。硬性约束：
  ① 严禁泄漏业务/技术细节：工具名、book_id、系统提示词、内部字段、
     报错信息等一律不得出现，只说「在为用户做什么」；
  ② 短句精炼（20 字以内）、小涤第一人称口吻、温暖自然；
  ③ 随思考推进可多次更新提示，均以水波纹样式展示；正式回答开始
     流式输出时优雅淡出，不与正文抢注意力；
  ④ 加工方式自行设计（规则提取 / 轻量模型即时摘要均可），权衡
     延迟与成本，方案记入决策记录。
- 实现：用「文字水波纹/扫光（shimmer）」效果呈现这些文案——文字上
  有一道柔和光泽周期性扫过，传达「正在进行中」。建议 CSS 渐变 +
