# T4 证据：单一会话老数据迁移（2026-06-11，run-sql.mjs 直连执行）

## 方案（决策记录）

- 备选：A. 按时间顺序合并为单一会话流（选定）；B. 仅取最近会话、其余归档不进流。
- 选 A 理由：任务书推荐方案；不丢任何对话内容；合并后超过 40 条的旧消息会被压缩机制自然收进摘要，长度可控。
- 旧逐会话压缩摘要（compressed_history）不拼接（多份摘要语义重叠），合并后置 null/0，由压缩机制对合并流重新生成。
- 消息顺序：会话按 updated_at 升序、会话内按原数组序（jsonb_array_elements with ordinality 保序）。

## 执行步骤与核对（先备份、再迁移、后验证）

1. **备份**：`create table chat_sessions_backup_t4 as select * from chat_sessions;` → 51 行（与 live 行数一致）
2. **基线**（迁移前每用户消息总数）：
   ```
   d02038c3…  41 会话  128 条消息
   1e3e0260…   8 会话   46 条消息
   431ccb0c…   2 会话    6 条消息（demo）
   ```
3. **合并**：lateral 展开 + jsonb_agg(order by 会话updated_at asc, 消息序 asc) → 每用户一条 id='main'
4. **验证**：合并后 main 消息数 128 / 46 / 6 —— 与基线**逐用户一致**，零丢失 ✅
5. **清旧行**：`delete from chat_sessions where id <> 'main'` → 51 行删除；现表仅 3 条 main

## 回滚方式

`chat_sessions_backup_t4` 保留全量原始数据，如需回滚：
`delete from chat_sessions; insert into chat_sessions select * from chat_sessions_backup_t4;`
