# AI 图书馆 · 产品优化迭代记录

> 视角：产品经理复盘。每项按 **问题（用户反馈/数据）→ 现状与根因分析 → 解决方案（含权衡）→ 收益与效果（尽量量化）** 展开。
> 项目：AI 图书馆 H5（goodcontent.cn）——AI 读书伙伴「小涤」对话（智学）、书城（泡馆）、沉浸式视频流（乱翻）。
> 本文档持续更新，新优化随做随补。

## 模块一：智学对话 Agent（核心体验）

### 1. 主对话模型选型迭代：MiniMax → Claude → 火山豆包-pro
- **问题**：用户反馈"回复慢、半天不出字"。实测经代理接入的 Claude 首字延迟 2~15 秒且极不稳定，出字仅约 42 字/秒；更早的 MiniMax 智能不足（卡片编排混乱）。
- **现状与根因**：首字延迟的大头不在模型本身，而在境外代理链路（vtok.ai）不稳；国内用户 ↔ 美区函数 ↔ 境外代理三段网络叠加。
- **解决方案**：搭建"热插拔模型评测基建"（同一套 20 项工具调用测试套件可一键换接入点评测任意模型），实测对比 Claude / 豆包-pro / 豆包-turbo 三者的工具调用可靠性、首字延迟、出字速率、人设口吻。豆包-pro 工具调用 20/20 全过、首字 0.4s 胜出；turbo 更快但荐书漏卡（19/20）被淘汰。保留 `CHAT_MODEL` 环境变量一键回退，MiniMax/Claude 代码全保留。
- **收益**：**首字延迟 15s → 0.4s（约 40 倍）**，出字速率 42→70 字/秒；后台任务（对话压缩/长期记忆/乱翻排序）同步切换统一模型栈，运维依赖减一。**方法论沉淀：模型选型必须用自家真实工具链实测，不能只看榜单。**

### 2. 联网搜索体系：从"质量差+泄漏事故"到"火山方舟流式直答"
- **问题**：①搜索结果质量差（旧 MiniMax 源，垃圾条目多）；②线上事故：回答里直接吐出原始 JSON（`{"results":...}`）给用户；③实时问题（天气/新闻）等待 12~17 秒且全程死水波纹。
- **根因**：②是自定义工具名 `web_search` 与 Claude 原生服务端工具撞名，代理层把原生搜索结果透传进正文；③是"火山跑一遍模型生成了完整回答→丢掉→再让主模型重写一遍"的双重耗时。
- **解决方案**：分三步。a) 工具改名 `web_lookup` 根治撞名（生产 0/5 泄漏验证）；b) 搜索后端切**火山方舟 Responses API**（字节系中文源：中国天气网/气象局/澎湃等，带精确发布时间，annotations 可溯源），并实测否决了 Claude 原生搜索（1/3 请求报错、常拒搜直接幻觉、海外源不适合中文用户）；c) 实时问句走 **Option B 流式直答**：火山那遍的回答直接以小涤口吻流式吐给用户+源卡，跳过二次作答。
- **收益**：搜索来源全部权威中文站；泄漏事故根治；**实时问答耗时约砍半（~6-7s 且边搜边出字）**；每次搜索成本压到约 5k token（关思考+限输出）。

### 3. 工具/卡片编排治理：从"反应式兜底堆叠"到"纯提示词+主动编排"
- **问题**：用户实锤截图：问天气却弹出上一轮的荐书卡（答非所问）；有时只出卡没正文；回答重复。
- **根因**：历史上为治各种失配，代码里堆了三层"反应式补救"（空回复重试/卡片失配补救/联网失配补救），互相叠加行为不可预测；模型换代后旧补丁反而制造新问题。
- **解决方案**（用户拍板"兜底全部取消"）：删除全部反应式补救（净删 166 行），只保留**主动编排**：实时问句首轮强制联网（防编造天气）、跑题荐书卡代码层拦截、同回答内卡片去重、轮次/时间预算护栏。行为全部由"提示词+工具描述+确定性编排"三处驱动。后经实测回补了唯一一层健壮性：模型偶发零输出时静默重试一轮（不猜错误、只重问）。
- **收益**：43 项回归全绿；问天气不再串书卡；架构从"补丁摞补丁"变为可推理、可维护。**方法论：兜底应当治"基础设施抖动"，不该治"模型行为"——后者交给提示词。**

### 4. 表达节制专项：荐一本给一本、概览不复读目录、三入口去重
- **问题**：用户截图三连：说"荐**一本**"却给三本卡；问"这本书讲什么"得到 1500+ 字的目录逐条复读（手机滑几屏）；回答结尾问"想先聊哪块？"、正文"要不要我拉原文"、章节卡"点开读原文"、追问气泡"拉原文我看看"——同一动作四个入口挤一屏。
- **根因**：荐书规则未约束数量意图；书单方案A后模型把目录概要全盘照搬；"下一步引导"没有统一归口。
- **解决方案**：a) 提示词"尊重数量"（说一本就一本讲透、卡片只放一本）；b) "消化转述"（概览两三百字讲透命题+框架+亮点，禁逐模块复述，相邻回合不重复同一框架）；c) 章节卡收敛（概览 1~2 张、细节≤3 张）；d) 新增 `suggest_replies` **快捷追问气泡**（2~3 个可一键发送的内容延伸短问题），并明确分工——**章节卡=读原文，追问气泡=接着聊**，气泡禁出"拉原文"类、正文禁结尾反问。
- **收益**：荐一本实测卡只 1 本；概览瘦身近半（1500+→约 800 字）；入口各司其职，用户不再选择困难。

### 5. 书单方案A：为 100 本书量级重构上下文（含防幻觉取料链）
- **问题**：书库即将从 7 本扩到 ~100 本。现状每次请求携带全量书单（每本 315 字概要），100 本≈3.5 万 token/请求——拖慢首字、烧钱、稀释模型注意力。
- **解决方案**：a) 书单改"一句话简介"（每本 ~80 字）：新增 `short_intro` 字段+批量生成脚本（豆包把 258 字概要压成 ≤30 字钩子句，幂等、默认干跑），并写入 import-books 导入流程（导入后自动补生成）；b) 新增 `get_book_briefs` 批量取料工具：荐书挑出候选后一次取全完整概要再写理由——**书单只剩一句话后，这是防止模型"凭一句话编书内容"的关键闸门**；c) 与答疑工具分工明确（briefs=横向比多本，toc=纵向钻一本）。
- **收益**：书单体积 **-70%**；39 项回归全绿、荐书理由质量不降（理由仍出自真实概要）；100 本导入后架构无需再动。

### 6. 断线治本：看资料回来，回答还在（两版迭代）
- **问题**：生成中用户点开来源网页，微信冻结页面杀掉流式连接→生成死掉，回来只剩半截+"断线了"。用户明确要求治本而非补丁。
- **方案 v1（后台生成+快照恢复）**：客户端带不可猜 UUID 凭证（genId）；服务端不再让客户端断连中止生成（waitUntil 续跑），进度快照（正文+卡片+完成态）按 2.5s 节奏写库（15 分钟 TTL）；客户端回前台凭 sessionStorage 里的凭证轮询快照回填原消息；「继续生成」按钮从断点续写兜底。生产实测：断连后快照持续增长至完成、可恢复。**教训：dev 与 Vercel 生产的断连行为不同（生产 enqueue 不报错），"断连才写快照"在生产一片都写不出——改为恒按节奏写。**
- **问题复发**：用户回来仍见"断线"。复盘发现 v1 的恢复是"回前台一次性判定"：微信解冻瞬间积压事件涌入，恢复逻辑误判"流还活着"便退出，此后无人再试——回光返照漏洞。
- **方案 v2（心跳+常驻看门狗）**：服务端生成期间每 3s 发心跳（思考/搜索静默期也发），"连接活着"恒有信号；客户端常驻看门狗每 3s 检查，**5 秒静默=连接必死**（零误判），自动接管恢复；流报错瞬间也立即尝试接管（顺利时用户根本看不到断线尾注）；全程留痕短代码（R0/R1/R2）便于复发定位。
- **收益**：生产验证心跳正常、断后快照可恢复；断线自愈时间上限约 5~7 秒；彻底告别"回来白等半截话"。

### 7. 等待体验体系化：让每一秒等待都"看得见在干活"
- **问题**：多处"死等"：联网搜索 7~12 秒死水波纹；生成中途模型出字间歇正文冻住（用户以为断线）；工具执行无状态提示。
- **解决方案**：a) 工具触发即给对应水波纹文案（为你挑书/翻看简介/翻阅图书/细读原文/整理章节/整理话头/联网搜索），补齐全部路径；b) 联网时显示**真实搜索词**（「正在搜「上海天气」」）；c) 流式卡顿呼吸点：出字停顿 >1.8s 在**最后一个字后面内联**浮现三个脉动小点（CSS ::after 挂任意末块——段落/列表项/引用都不换行），恢复出字即消失。
- **收益**：等待从"黑盒焦虑"变"过程可感"；呼吸点流畅时零打扰、卡住时即时安抚。

### 8. 渲染质量兜底：中文场景的 Markdown 加粗碎裂
- **问题**：正文频繁出现裸 `**` 星号（如 `**《消费、休闲和摆设》**` 原样显示）。
- **根因**：CommonMark 边界规则对中文标点不友好——加粗符号紧贴《 " 等标点时**标准本身判定加粗不成立**，提示词无法 100% 约束模型输出。
- **解决方案**：渲染层 `fixCjkBold` 预处理——仅在"必定渲染失败"的位置按需插入视觉无感的极细空格（U+2009），正常加粗零影响；6 组真实坏例单测全过。
- **收益**：满屏星号绝迹。**方法论：模型输出的格式问题，渲染层兜底优于提示词说教。**

### 9. 冷启动引导：开场白 + 情绪型快捷入口
- **问题**：游客/零阅读记录新用户进入智学只看到标题，不知道能干嘛；引导问题全是"围绕书名"的，可新用户往往只知道"自己哪里不舒服"。
- **解决方案**：a) 补新用户版开场白气泡（一句破冰讲清能怎么用，纯本地拼装零成本）；b) 引导 chips 混入 1 条"情绪/求助型"入口（「最近焦虑内耗读什么好」「道理都懂做不到」），随机轮换、恒在前 3 位（50 轮单测验证）。
- **收益**：最低门槛入口直达"对症荐书"这一最能打动用户的能力；有阅读记录用户仍是个性化近况开场。

## 模块二：语音输入

### 10. 流式语音架构：从"松手等 5 秒"到"边说边出字"
- **问题**：初版录完再识别，松手后"…"长等待。
- **解决方案**：自建流式链路——浏览器采 PCM →Supabase Edge Function 中继（解决浏览器无法携带鉴权头直连的限制）→火山流式 ASR，实时回传边说边出字；识别端点/资源号经逐一实测踩通（bigmodel_async + seedasr.sauc.duration）。
- **收益**：说话过程实时出字，松手基本即得全文。

### 11. 丢字/失败专项（三轮迭代打磨）
- **问题**：用户多轮反馈：首次长按不识别；开口太快丢前几个字；偶尔整句失败弹"没听清"。
- **根因逐层剥**：①冷启动竞态（授权弹窗打断手势、中继 isolate 冷启动、AudioContext suspended 采到静音）；②**拾音晚于开口**：长按判定+开麦+建音频图要 600~900ms，用户看到面板就开口，前几个字物理上没被录到；③中途 WS 断线无补救；④松手等待窗从松手起算，冷链路下"话录到了却被判没听清"。
- **解决方案**：a) **按下即预拾音**（pointerdown 就开麦+连 WS 采音进缓冲，280ms 判定通过无缝转正；判定为点按立即关麦——代价仅系统麦克风指示灯闪现，已向用户说明并获认可）；b) AudioContext 常热复用（此前"每次松手关闭"的修复曾造成回退，公开复盘）；c) 整句 PCM 内存留底（≤60s≈2MB）+断线自动重拨重发；d) 等待窗自适应（有实时文字 600ms 秒发；零文字从 EOS 送达起算 6s）；e) 中继 75s 保温心跳；f) 完整性存疑时回填输入框让用户确认，不擅自发送（半句也不浪费）。
- **收益**：丢字归零、松手到发送快 0.5~1 秒、冷链路不再误报；三条离开路径（点按/滑走/系统手势）全部防麦克风泄漏。
- **PM 复盘**：中间一次修复（await resume）治了 A 却弄坏了 B，被用户抓到"体验倒退"。教训沉淀：**每次改动必须列出"可能影响的相邻路径"并逐条推演，改后跑全量回归。**此后引入"独立对抗评审"流程。

## 模块三：乱翻（沉浸视频流）

### 12. 自动播放与声音策略
- **问题**：进入乱翻有时自动暂停、有时自动静音，需要手动点。
- **根因**（四条链）：①浏览器禁止无手势带声自动播放，入场点击的"手势余温"（~5s）时灵时不灵；②iOS/微信的带声许可**按 video 元素记**，而页面复用 3 个元素轮播，只有第一个被手势"祝福"过；③系统对"无手势开声"会直接暂停视频，而自动补播是裸 play 无兜底→卡死无按钮；④提示"轻点开启声音"，但轻点又被单击判定成暂停——提示自相矛盾。
- **解决方案**：手势内静音解锁整个视频池（起播即停，顺带暖缓冲）；触摸监听升到页面级并用 data-nokick 排除控件（防"点声音钮反而全局静音"——该问题由独立对抗评审发现）；政策暂停走带静音兜底的自愈通道（保持当前静音态，拔耳机不突然外放）；静音态首次轻点=开声不暂停（按手势快照判定，不吞真实暂停意图）。
- **收益**：连滑不再中途静音、不再冻住无按钮；经对抗评审修复 4 个必修点后上线。

## 模块四：性能与全局体验

### 13. 跨太平洋链路优化的失败与回滚（公开复盘）
- **问题**：生产首字 4.4s（函数在美区，流式往返太平洋）。
- **过程**：迁移函数区域到香港 hkg1——上线后**全站 502**：香港机房连不通火山北京端点。20 分钟内回滚恢复。
- **教训**：跨区迁移必须先在目标区域实测所有下游依赖可达性，不能只看"离用户更近"。提速改走"不动区域"的路径（见 #2 Option B、#14 预载）。

### 14. 进站预加载：泡馆/智学"秒开"
- **问题**：进泡馆/智学要等接口和封面图逐张蹦出。用户提议"开屏页加载完再进"。
- **方案权衡**：否决"强制开屏等待"（把卡顿变成强制等待，总时长不变还更烦），改为"**进来先看到东西，空闲时把别处悄悄备好**"：底部导航（四页共有）挂一次性 requestIdleCallback——预取首页数据（泡馆与智学欢迎区共用一份，一次两页暖）、预热前 8 张封面图、预取四个 Tab 的页面 JS、空转一次乱翻查询暖链路。失败无感回退现载。
- **收益**：切页不再等接口/图片；零阻塞、弱网无副作用。

### 15. 信息呈现细节打磨
- **问题与方案合集**：联网多次搜索出多张来源卡难对应（→豆包式聚合一张卡、按搜索词分组、卡头"搜索 N 个关键词·参考 M 篇"）；章节卡头语义模糊（→「引用 N 章 · 点开读原文」：前半溯源+数量，后半行动指引）；回答被截断只能重新生成（→「继续生成」从断点续写，不丢已生成内容和卡片）。
- **收益**：溯源清晰、行动明确、失败可恢复。

## 附：工程方法论沉淀（面试可讲的"打法"）

1. **实测驱动选型**：模型/搜索后端/区域迁移全部用自家真实链路实测（工具调用套件、TTFT/出字速率、可达性），拒绝拍脑袋。
2. **回归测试资产化**：沉淀 39 项行为回归套件（卡片命中/求助场景/工具调用）+断线 e2e+渲染单测，每次改动全量跑，红了不上线。
3. **独立对抗评审**：高风险改动（乱翻手势、断线恢复）交独立评审员专门"推翻"，两次各抓出 3~4 个必修缺陷后才上线。
4. **兜底哲学**：代码兜底只治基础设施抖动（空回复、断线），模型行为问题交给提示词+工具描述+确定性编排；反应式补丁坚决清除。
